# 構築ログ 2026-09-07

## 1. CI でのコンソールログ抑止(public Actions ログ対策)

ユーザー指示: 「gh actions 上ではログは出ないようにしてほしい。ローカルではいいんだけど
public で見えちゃうので」。GitHub Actions の実行ログは public リポジトリでは
誰でも閲覧できるため、それまでの実装では**実サイトのドメイン・検索 URL・スレタイ・
gist URL がログに表示される**状態だった。

### 対応

- `index.mjs` / `notify.mjs` / `run-log.mjs` の console 出力を `log()` / `warn()` /
  `error()` ラッパーに差し替え。環境変数 `CI`(GitHub Actions が自動で設定)が
  ある場合は**一切出力しない**
- ローカル(CI 変数なし)は従来どおり全文表示される
- エラー内容・統計は `log/latest-run.md` にマスク済みで記録されるため、
  Actions が無音でも実行状況は追える
- ワークフローの shell ステップの echo は復元成功/ログ更新の案内のみで
  機微情報を含まないためそのまま

### 検証(/tmp にコピーした scraper で実施)

- `MOCK=1 CI=1` で scrape → **出力ゼロ**(サマリ JSON は正常生成)✓
- `CI=1` で notify / run-log → 出力ゼロ(サマリ追記・Markdown 生成は正常)✓
- CI なし → 従来どおりログ表示 ✓
- `node --check` 3 ファイル OK ✓

### 補足

- sed での一括置換時にラッパー定義自身が自分を呼ぶ再帰になっていたのを検知・修正
  (`const log = () => log(...)` → `console.log`)。`node --check` では検出されないため、
  実行テストでの確認が重要

## 2. CI ログの変更: 全沈黙 → 処理ステップは出す(機微情報のみ除外)

ユーザー指示: 「どこで止まったかがわかるように、処理ステップは出してほしい。
掲示板から抜き出した情報は出さないようにしてほしい」。section 1 の全沈黙方式を
変更し、**進行状況は表示しつつ機微情報のみ除外**する方式にした。

### CI(GitHub Actions)での表示

```
[scraper] 実サイト で実行します          ← ドメインは出ない
[scraper] キーワード検索: 梅田 / 天王寺   ← キーワード自体は問題ない(ユーザー指定値)
[scraper] スレッド合計: 20 件
[scraper] フィルタ後: 20 件
[scraper] (1/20) スレ詳細取得中          ← スレタイは出ない
[scraper] 完了: 20 件中 3 件の詳細を…    ← レス本文・メールも出ない
```

- 失敗時: エラーメッセージの URL は `maskUrl()` で `***` にマスクして表示
  (例: `*** の取得に失敗しました: fetch failed`)— どこで止まったかが分かる
- notify: `[notify] Gist を作成しました`(URL は省略)/ 件数・スキップ理由は表示
- ローカル(CI 変数なし)は従来どおりスレタイ・URL・gist URL も表示(`showDetail`)

### 実装

- 全ログ沈黙の `quiet` ラッパーを廃止して console 直戻しにし、機微情報を含む
  個所のみ `showDetail = !process.env.CI` で分岐(対象 URL・検索 URL・スレタイ・
  スレ URL・gist URL)
- エラー系の console.warn はローカル/CI とも `maskUrl()` 済みの文字列を出す
  (サマリ errors と同一の文字列で二重管理なし)

### 検証(/tmp にコピーした scraper で実施)

- `CI=1` モック実行 → 上記のとおりステップ表示あり・スレタイ/URL なし ✓
- `CI=1` で到達不能ドメイン → `*** の取得に失敗しました: fetch failed` で途中まで
  進んでいることが分かる ✓
- CI なし → スレタイ・URL 表示 ✓
- notify `CI=1` → gist URL 非表示 ✓ / `node --check` 3 ファイル OK ✓

## 4. 巡回設定 gist(keywords / sexExcludes を gist で管理)

ユーザー指示: 「フィルターするキーワードや検索する地名を gist から取得するように
したい。gist に json をおいておいてそこに特定の設定を書いておくスタイル」。
「設定 gist の URL はシークレットに入れる」「gist の URL もログには出さない」。

### 使い方

- リポジトリシークレット(または `.env`)に **`SCRAPER_SETTINGS_GIST_URL`** を設定
  (`https://gist.github.com/<user>/<id>` 形式。gist ID 直接指定も可)
- gist 内の**最初の `.json` ファイル**に以下を書く(編集は gist を直すだけ。再デプロイ不要):

  ```json
  {
    "keywords": ["地名1", "地名2"],
    "sexExcludes": ["排除したい性別の値"]
  }
  ```

- 優先順: 環境変数(`SCRAPER_KEYWORDS` / `SCRAPER_SEX_EXCLUDES`) > gist > config
- 秘密 gist を読むため `GIST_TOKEN`(PAT)が必要(scrape.yml の Scrape ステップにも追加)

### 実装(index.mjs)

- `loadGistSettings()`: `GET {GIST_API_URL}/{gistId}`(テスト用の `GIST_API_URL` 差し替えは
  notify と同じ変数を流用)→ 最初の `.json` ファイルの content をパース
- `splitList()`: 配列/カンマ文字列の両方を受けて正規化
- **gist URL・ID・取得内容はログに出さない**(秘密 gist は URL を知れば閲覧可のため)。
  失敗メッセージにも URL/ID を含めない(例: `設定 gist の取得に失敗しました (HTTP 404)`)
- **読み込み失敗時は実行を中止**(exit 1): 設定 gist が読めないまま意図しない
  フィルタで巡回・通知されるのを避けるため。エラーは log/latest-run.md にも記録
- サマリに `settingsGist: true/false` を追加 → `log/latest-run.md` に
  「巡回設定: 設定 gist から読み込み」と表示
- notify.mjs: 投稿用 gist URL を**ローカルでもログに出さない**ように統一
  (「Gist を作成しました(新着 N スレ)」のみ)

### 検証(ダミー gist API サーバ、/tmp で実施)

- gist 由来のキーワード 2 件でスレ検索 URL が組み立てられる ✓
- 環境変数 `SCRAPER_KEYWORDS` 指定時は環境変数が優先される ✓
- gist 由来の性別排除(「男」)で 5 件/スレ除外 ✓(サマリ `sexExcluded: 10` / `settingsGist: true`)
- gist が 404 → `設定 gist の取得に失敗しました (HTTP 404)` で実行中止・URL 非表示 ✓
- `log/latest-run.md` に「巡回設定: 設定 gist から読み込み」表示 ✓
- `node --check` 3 ファイル + scrape.yml YAML 検証 OK ✓
- Worker(系統①)は未対応(バッチ側のみ)

## 5. メールアドレス ブラックリスト(blackList)

ユーザー指示: 設定 gist に `blackList`(メールアドレス配列)を追加し、**該当する
メールアドレスを持つレスを結果から除外**したい。

### 使い方(設定 gist の JSON)

```json
{
  "keywords": ["地名1", "地名2"],
  "sexExcludes": ["排除したい性別の値"],
  "blackList": ["排除したいメールアドレス"]
}
```

- 優先順: 環境変数 `SCRAPER_BLACKLIST`(カンマ区切り)> gist > config.filters
- **完全一致**(大文字小文字・前後の空白は無視)。メールを持たないレスは対象外
- 判定は `parse.mjs` の `isBlacklisted(post, filters)`(共有)。ただし **post.email は
  個別メールページ(C)の取得後に確定するため、実質バッチ専用**(Worker はメール
  ページを取得しないので、ブラックリストは効かない)
- 処理順: 性別排除(メールページ取得前)→ メール抽出 → ブラックリスト除外。
  ブラックリスト該当レスは 1 レス = 1 リクエストのメールページを取ったうえで
  除外される(性別排除と違いリクエストは発生する)
- サマリに `blackListed` 件数を追加 → `log/latest-run.md` に
  「ブラックリスト: N 件を除外」と表示(該当があったときのみ)

### 検証(/tmp にコピーした scraper + ダミー gist サーバで実施)

- gist 由来の blackList でモック実行 → 各スレ 7 件除外、出力 JSON に当該メールなし ✓
  (サマリ `blackListed: 21` / 残ったレスの email は空欄)
- 一致ルール: 完全一致 / 大文字小文字無視 / 前後空白トリム → true、
  別アドレス・email 空・email なし → false ✓
- ブラックリスト未設定時は従来動作のまま(フィルタなし)✓
- `node --check` 3 ファイル + scrape.yml YAML 検証 OK ✓

## 6. cron 高頻度化(5 分おき) + 通知 gist を投稿者ごとに変更

ユーザー指示: ①「`7 * * * *`(毎時)は遅い。GitHub Actions で実行できる最小頻度に」
②「最終的な gist の一覧はスレごとではなく**投稿者ごと**に。元投稿スレがどこだったか
は投稿に付与するイメージ」。

### ① cron 頻度

- `scrape.yml` の schedule を `7 * * * *`(毎時)→ **`2-59/5 * * * *`(5 分おき)**。
  GitHub Actions の cron で設定できる最短間隔は約 5 分
  (それより短い cron は実行が保証されない)
- `2-59/5` で正時の `:00`/`:30` を避けて 2 分ずらしで開始(全ユーザーの集中時間帯を回避)
- **注意**: 5 分おきの実行は対象掲示板へのアクセス頻度が上がる。リクエスト間隔
  (`request.intervalMs`, 既定 1500ms)はバッチ内で守られるが、全体の負荷は 12 倍に
  なる点は要観察。ダメそうなら戻す

### ② 通知 gist を投稿者ごとに

- `notify.mjs` の `buildGistContent()` を再構成: 新着スレのレスを**投稿者名ごと**に
  グループ化(`groupPostsByAuthor()` 名前順 Map。空名前は「(名前なし)」)。
  同一投稿者が複数スレに書き込んでいる場合はスレ単位で束ねて出力
- 各レスの見出しに**元投稿スレ**(タイトル・URL・カテゴリ)を付与:
  `## 投稿者名(N レス)` → `### 元スレ: <スレタイ>` + URL
- 見出し: `# 新着投稿 N 件(投稿者 M 名 / 新着スレ K 件)`
  (初回実行時は従来どおりの案内文)
- **本文未取得スレ**(詳細取得に失敗したスレ)は投稿者一覧に出せないため、
  「本文未取得スレ: N 件(以下の投稿者一覧には含まれない)」を冒頭に明記
  (旧実装ではスレ見出し + 「詳細はありません」を載せていた)
- gist ファイル名を `new-threads-*.md` → `new-posts-*.md` に変更。
  description はスレ数のみ(投稿者名・投稿内容は gist metadata に載せない)
- Discord への投稿は変更なし(「更新がありました。+ gist URL」のみ)
- 状態管理(.scrape-state.json)・既知スレ判定はスレ単位のまま(投稿者ごとではない)

### 検証(ダミー gist/webhook サーバ、/tmp で実施)

- モック 20 スレ(うち詳細 3 件)を初回実行 → 投稿者ごとにグループ化、
  各グループ内で元スレ見出し + URL 付き ✓(description は `public: false` ✓)
- 詳細未取得の新着 1 スレのみの実行 → 「新着投稿 0 件」+ 本文未取得の明記 ✓
- Discord POST 本文は gist URL のみ ✓ / `node --check` + YAML 検証 OK ✓

## 8. 自動投稿(系統③ — Playwright + 設定 gist の post ブロック)

ユーザー指示: 投稿フォームの HTML をもとに「Workers の適当なパスにアクセスしたら
フォームに自動投稿される仕組み」を作りたい。**定期投稿の設定は gist で管理**、
**自動操作は puppeteer/playwright を使用**。

### 実行環境の判断

- **Playwright/puppeteer は Cloudflare Worker 内では動かない**(ブラウザバイナリが
  必要のため)。Cloudflare Browser Rendering(有料)なら Worker 内で可能だが、
  **無料プランの GitHub Actions + Playwright** を採用(ユーザー選択)
- cron は系統②と同じ `scrape.yml` に統合。ブラウザ(~150MB)は actions/cache
- 「Worker パスから投稿を起動」したい場合は後から repository_dispatch 連携を追加可能

### 使い方(設定 gist の JSON に post ブロックを追加)

```json
{
  "keywords": [...], "sexExcludes": [...], "blackList": [...],
  "post": [
    {
      "name": "系統A",
      "threadIds": ["投稿先スレ ID"],
      "formPath": "/public/comment/?id={id}",
      "intervalMinutes": 180,
      "posts": [
        {
          "fields": {
            "name": "…", "email": "…", "sex": "…", "age": "…",
            "type": "…", "free_category1": "…", "free_category2": "…",
            "content": "…", "edit_password": "…"
          },
          "sage": true
        }
      ]
    }
  ]
}
```

### 追加: post は複数系統(配列)で書ける(ユーザー指示)

- `post` はオブジェクト(1 系統)でも**配列(複数系統)**でも受け付ける。
  各系統は投稿先スレ・間隔・投稿パターンを独立に持ち、投稿状態
  (前回投稿時刻・ローテーション番号)も系統ごと(`name` キー。省略時 `#0` …)
- 各系統に `enabled: false` を書くとその系統だけ無効化できる
- 実行サマリは全系統の合計(posted/failed)+ `notDue`(間隔未経過で
  スキップした系統数)を記録

- フィールド名はフォームの **name 属性そのもの**(`name` / `email` / `sex` / `age` /
  `type` / `free_category1` / `free_category2` / `content` / `edit_password`)。
  select は値で選択(失敗時は表示ラベル)、checkbox は truthy、text/textarea は fill
- `posts` は複数パターンを置け、**ローテーション**で選択(rotateIndex を状態に保存)
- `intervalMinutes` ごとに 1 回(スレ数分)。**成否問わず試行時刻を記録**するため
  失敗しても間隔内に再試行されて掲示板を連打することはない
- ドメインは `SCRAPER_DOMAIN`(シークレット)から、フォームパスは gist の
  `formPath`(既定 `/public/comment/?id={id}`)で組み立て

### 実装(poster/index.mjs)

- Playwright で `form[name=form01]` を操作: フィールド投入 → csrf_token は
  ページの hidden のまま送信 → submit → **送信後も空フォームが見えたら失敗扱い**
- 投稿内容(名前・メール・本文・編集キー)は**ログに絶対に出さない**(件数のみ)。
  エラー内の URL も `maskUrl()` でマスク(CI・ローカル共通)
- 実行サマリに `post: {status, posted, failed, patterns, targets, intervalMinutes}` を
  追記 → `log/latest-run.md` には件数のみ反映(RUN_LABELS に追加済み)
- `npm run post` で単体実行。`npm run batch` は scrape → notify → post の順に変更
- Actions: `scrape.yml` に Playwright ブラウザのキャッシュ + Auto post ステップを
  追加。状態 `.post-state.json` を `.scrape-state.json` と同じ actions/cache で管理

### 検証(ダミー投稿フォームサーバ + ローカル Playwright Chromium で実施)

- ユーザー提供のフォーム HTML(ダミー化)をローカルサーバで配信 → gist 相当の
  post 設定で実行 → **全系統のフィールドが正しく送信されることをダミー側で確認**:
  name/email/text、sex・age・type・free_category1・free_category2 の select(値選択)、
  content(改行を含む textarea)、edit_password、sage チェックボックス、
  hidden の csrf_token を含む multipart POST ✓
- 複数系統: 系統A(間隔 0 分=即投稿)/ 系統B(intervalMinutes 999999)→
  A は投稿、B は「次の投稿まで約 N 分のためスキップ」✓(サマリ `notDue: 1`)
- **パターンローテーション**: 1 回目 pattern 1 → 2 回目 pattern 2 が送信される ✓
- 状態ファイル: 系統ごとに `lastPostedAt` / `rotateIndex` が保存される ✓
- `log/latest-run.md` 生成 → `- 自動投稿: 実行あり(1 成功 / 0 失敗)` ✓
- 手元コンテナは `npx playwright install-deps chromium` が必要だった
  (GitHub Actions の ubuntu-latest は deps プリインストールのため不要)
- `node --check` + YAML 検証 OK ✓

## 10. メインスレの直接巡回(directThreads + 降順ページング対応)

ユーザー指示: 「次にこちらは定期スクレイプのページと対象として追加したいです」+
「今追加したこちらはメインスレみたいな感じで、従来の地域別スレとはべつになります」。
地域別スレ(キーワード検索で巡回)とは別に、**一覧を経由しない巨大な「メインスレ」**
(スレ 1 本が 1897 ページに及ぶ板形式)を毎回巡回対象に追加したい。

### メインスレの構造(従来スレとの差分)

- URL 形式・チャンク構造(`<hr>` 分割、`span[id^='b']`、`[名前]`、meta 行)は
  従来の B ページと同一 → パーサーは共有のまま
- **ページ送りが降順**: p=1 が最新、`→` が過去ページ(従来は p=1 が最古の昇順で、
  最終ページから遡る実装のため、そのままでは p=1897 を取得しに行く)
- **チャンク内の行順が逆**: 日時行 → レス番号行(従来は番号行が先頭)。
  従来の `numberPattern: ^\s*(\d+)` は日時行の「2026」にマッチしてレス番号・
  日時が壊れていた
- 追加メタ: `地域 ：値` 行(従来の B ページにはない。`metaPatterns.area` を追加)
- スレタイ要素なし(`<title>` のみ)→ config の `title` をフォールバック使用

### 実装

- `config.directThreads`(配列)を追加: 要素は URL 文字列 or
  `{url, title, newestFirst}`。フィルタ済みスレ一覧の**末尾に追加**され
  通常スレと同一フロー(詳細取得・メール抽出・ブラックリスト・通知)に乗る
  - 明示指定のため `matchesFilters`(タイトルフィルタ)は適用しない
  - 一覧由来スレと ID 重複時は一覧側を優先(スキップ)
  - `category`(出力 JSON)は `(直接指定)`、タイトルは `title` 値
- `index.mjs` `fetchThreadDetail()`: `newestFirst` スレは p=1 → p=2 → … の
  降順取得にし、**1 ページ全部が maxAgeDays 範囲外になったページで打ち切り**
  (降順なのでそれより古いページも範囲外のため)。maxThreadPages 上限は共通。
  タイトルはパース結果が空なら `thread.title` をフォールバック
- `parse.mjs`: 日時行がレス番号行より前にある形式のため、番号行以降に
  日時が見つからないときチャンク全体から最初の日時をフォールバック抽出。
  本文は番号行以降のみなので前の日時行が本文に混入しない
- `config.example.json`: `numberPattern` を `^\s*(\d+)` → **`(\d+)\s*\[`** に変更
  (レス番号行は必ず `[名前]` を伴うため日時行と区別できる。従来形式
  「24[t◆…][編集]…」も同じパターンで取れる) + `metaPatterns.area` +
  `directThreads: []` の追加
- **Worker(系統①)は未対応**(バッチ側のみ。CLAUDE.md に記載済み)
